# Rule 100400 — Scheduled Task Detection

## MITRE ATT&CK Mapping

| Field | Details |
|---|---|
| Rule ID | `100400` |
| Technique | **T1053.005 — Scheduled Task/Job: Scheduled Task** |
| Tactic | **Persistence** |
| Wazuh Level | **8** |
| Data Source | Windows Sysmon process creation telemetry |
| Primary Process | `schtasks.exe` |
| Detection Trigger | `/create` argument |
| Validation Result | **Successfully Fired** |

---

## 1. Detection Objective

The objective of Rule 100400 was to detect the creation of scheduled tasks through `schtasks.exe` when the `/create` argument is present in the command line.

Scheduled tasks are legitimate Windows functionality, but they can also be abused by attackers to establish persistence or execute commands automatically.

The detection was therefore designed to identify a specific observable behavior associated with scheduled-task creation.

---

## 2. MITRE ATT&CK Technique

**T1053.005 — Scheduled Task/Job: Scheduled Task**

**Tactic:** Persistence

Scheduled tasks can provide attackers with a mechanism to execute commands or programs automatically based on a configured trigger.

In this project, the detection focused on the use of the Windows `schtasks.exe` utility with the `/create` argument.

---

## 3. Detection Logic

The rule was designed around process-creation telemetry.

The key indicators were:

```text
schtasks.exe
```

and:

```text
/create
```

The detection therefore looks for `schtasks.exe` execution where the command line indicates that a new scheduled task is being created.

The project used Sysmon process-creation telemetry as the primary data source.

---

## 4. Detection Rule

The custom Wazuh rule was created in the Wazuh manager's local rules configuration.

The rule was mapped to:

```text
T1053.005
```

and assigned Wazuh level:

```text
8
```

The rule description identifies scheduled-task creation through `schtasks.exe` as a possible persistence mechanism.

---

## 5. Rule Validation

Before testing the detection, the Wazuh configuration was validated using:

```text
wazuh-analysisd -t
```

This confirmed that the configuration could be loaded without errors.

The rule was then tested using Atomic Red Team in the isolated Windows lab environment.

---

## 6. Attack Simulation

Atomic Red Team was used to simulate the scheduled-task behavior associated with T1053.005.

The simulation created two scheduled tasks:

```text
T1053_005_OnLogon
T1053_005_OnStartup
```

The tasks were configured to launch `cmd.exe` when their respective triggers occurred.

An example of the observed command-line behavior was:

```text
schtasks /create /tn "T1053_005_OnStartup" /sc onstart /ru system /tr "cmd.exe /c calc.exe"
```

The telemetry showed:

```text
Image:
C:\Windows\System32\schtasks.exe
```

with the `/create` argument present in the command line.

---

## 7. Detection Result

### Status: Successfully Fired

The Wazuh detection fired twice during the test.

This occurred because the simulation created two scheduled tasks:

1. `T1053_005_OnLogon`
2. `T1053_005_OnStartup`

The detection therefore successfully identified the scheduled-task creation behavior.

## 8. Alert Investigation

When investigating the alert, the following information is relevant:

- Rule ID
- Timestamp
- Endpoint
- User/account
- Process image
- Command line
- Parent process
- Scheduled-task name
- Trigger type
- Executed command

The command line is particularly important because it provides context about what was being created and what would execute when the task was triggered.

---

## 9. SOC Alert Triage

The alert was classified as a:

**True Positive**

because the observed activity matched the behavior the detection rule was specifically designed to identify.

For the controlled project simulation, the activity was expected and authorized.

In a real SOC environment, the analyst would determine whether the scheduled-task creation was authorized before escalating or closing the alert.

### Recommended Investigation

The analyst should determine:

- Was the task creation authorized?
- Which account created the task?
- What program or command will the task execute?
- What trigger was configured?
- Is the task associated with known administrative activity?
- Are there other suspicious events on the same endpoint?

---

## 10. Severity Assessment

The Wazuh rule was assigned level:

```text
8
```

This places the detection in the project's higher-priority range and reflects the potential relationship between scheduled-task creation and persistence.

The final severity should still be considered alongside the surrounding context.

A legitimate scheduled task created during authorized administration may not represent malicious activity.

---

## 11. False Positive Considerations

Scheduled tasks are commonly used by:

- Windows
- Microsoft software
- System administrators
- Enterprise applications
- Security software
- Update mechanisms

Therefore, detecting every scheduled-task creation does not automatically mean that malicious persistence has occurred.

An analyst should investigate the task name, creator, command, timing, and surrounding activity before making a final determination.

During the project, a constructed false-positive scenario was also used for triage practice involving a SYSTEM-created task during a confirmed Windows Update window.

The task was verified against the known patch window before being closed.

## 15. Detection Engineering Takeaway

```text

     ↓
T1053.005 Scheduled Task
     ↓
Identify Observable Behavior
     ↓
schtasks.exe + /create
     ↓
Create Wazuh Detection Rule
     ↓
Simulate with Atomic Red Team
     ↓
Collect Sysmon Telemetry
     ↓
Wazuh Alert
     ↓
Investigate
     ↓
Classify as True Positive
```

The successful validation demonstrated that the custom Wazuh rule could identify the targeted scheduled-task creation behavior in the Windows endpoint telemetry.

---

## 16. Lessons Learned

This detection reinforced several important SOC and detection-engineering concepts:

- Detection rules should focus on observable attacker behavior.
- MITRE ATT&CK provides a useful framework for mapping detections to adversary techniques.
- Process-creation telemetry provides valuable context for endpoint detections.
- A triggered alert still requires investigation and contextual analysis.
- Legitimate administrative activity can resemble attacker behavior.
- Detection engineering and alert triage must work together.
- Cleanup is important after controlled adversary simulation.
