# Rule 100404 — LSASS Credential Dumping Detection

## MITRE ATT&CK Mapping

| Field | Details |
|---|---|
| Rule ID | `100404` |
| Technique | **T1003.001 — OS Credential Dumping: LSASS Memory** |
| Tactic | **Credential Access** |
| Wazuh Level | **15 — Critical** |
| Primary Process | `rundll32.exe` |
| Detection Logic | `comsvcs.dll` + `MiniDump` |
| Data Source | Windows Sysmon process-creation telemetry |
| Validation Result | **Blocked by Windows Defender** |

---

## 1. Detection Objective

The objective of Rule 100404 was to detect a potential LSASS memory-dumping technique involving `rundll32.exe`, `comsvcs.dll`, and the `MiniDump` function.

LSASS memory dumping is associated with credential-access activity because successful dumping of the LSASS process can expose authentication material from memory.

The detection was therefore designed to identify a specific process and command-line pattern associated with this behavior.

---

## 2. MITRE ATT&CK Technique

**T1003.001 — OS Credential Dumping: LSASS Memory**

**Tactic:** Credential Access

The technique focuses on obtaining credential material from the Windows Local Security Authority Subsystem Service (LSASS).

Because successful credential dumping can expose sensitive authentication information, this behavior is considered high risk.

---

## 3. Detection Logic

The custom rule monitors process-creation telemetry and looks for a combination of:

```text
rundll32.exe
```

and:

```text
comsvcs.dll
```

with:

```text
MiniDump
```

The rule therefore attempts to identify a command-line pattern associated with LSASS memory dumping.

The detection is mapped to:

```text
T1003.001
```

and assigned Wazuh level:

```text
15
```

---

## 4. Detection Rule

The custom Wazuh rule was created in the Wazuh manager's local rules configuration.

The rule logic was:

```xml
<rule id="100404" level="15">
    <if_group>sysmon_event1</if_group>
    <field name="win.eventdata.image" type="pcre2">(?i)\\rundll32\.exe$</field>
    <field name="win.eventdata.commandLine" type="pcre2">(?i)comsvcs\.dll.*MiniDump</field>
    <description>Custom rule: Possible LSASS memory dump via rundll32/comsvcs.dll</description>
    <mitre>
        <id>T1003.001</id>
    </mitre>
</rule>
```

The rule uses Sysmon Event ID 1 process-creation telemetry.

---

## 5. Rule Validation

Before testing the detection, the Wazuh configuration was validated using:

```text
wazuh-analysisd -t
```

The configuration was accepted without syntax errors.

The detection was then tested against the Windows endpoint in the isolated laboratory environment.

---

## 6. Attack Simulation

The project attempted to simulate LSASS memory dumping using Atomic Red Team.

The technique was also attempted manually to determine whether the failure was specific to the Atomic Red Team tooling.

The controlled command attempted was:

```text
rundll32.exe C:\Windows\System32\comsvcs.dll, MiniDump 596 C:\Windows\Temp\lsass_test.dmp full
```

The objective was to invoke the `MiniDump` functionality through `comsvcs.dll` against the LSASS process.

---

## 7. Simulation Result

### Status: Blocked by Windows Defender

The attempted execution did not successfully execute.

The Windows endpoint returned:

```text
Access is denied
```

The same blocking behavior was observed during both:

1. Atomic Red Team execution
2. Direct manual execution

This demonstrated that the prevention was consistent and was not simply an issue with the simulation tool.

---

## 8. Detection Validation Status

### Important Distinction

**Rule 100404 was created and configured, but it was not successfully validated through a live-fire detection.**

Windows Defender prevented the underlying LSASS dumping behavior before the expected process execution could occur.

Therefore:

```text
Rule Created
      ↓
Configuration Validated
      ↓
Attack Attempted
      ↓
Windows Defender Blocked Execution
      ↓
No Successful Live-Fire Detection
```

The project deliberately did not disable or weaken Windows Defender to force the test to succeed.

---

## 9. Why This Is Not Automatically a Detection Failure

A successful SIEM detection requires the underlying behavior to generate observable telemetry that reaches the SIEM.

In this case, Windows Defender prevented the targeted behavior before successful execution.

Therefore, the test demonstrated:

**Endpoint Prevention**

but did not provide:

**Successful Wazuh Detection Validation**

These are two separate security outcomes.

---

## 10. SOC Significance

An LSASS memory-dumping attempt should be treated as a high-priority security event in a real SOC.

The project assigned the rule Wazuh level:

```text
15
```

This places the detection in the project's Critical severity range.

The project triage criteria identify credential theft or dumping as activity requiring immediate escalation and consideration of containment.

---

## 11. SOC Alert Triage

If Rule 100404 were triggered in a production environment, the analyst should investigate:

- Endpoint
- User account
- Process
- Parent process
- Command line
- Process creation time
- Related PowerShell activity
- Related credential-access alerts
- Authentication activity
- Other suspicious processes
- Evidence of successful execution

The analyst should also determine whether the activity was authorized security testing or potentially malicious credential-access activity.

---

## 12. Recommended Response

If the activity is unexpected or unauthorized:

1. Preserve relevant telemetry.
2. Identify the account responsible.
3. Investigate the parent process.
4. Search for related credential-access activity.
5. Determine whether LSASS access succeeded.
6. Check for evidence of credential theft.
7. Escalate the alert.
8. Consider containment if compromise is suspected.
9. Document the investigation.

## 16. Detection Engineering Decision

No tuning was performed on Rule 100404.

The project determined that the failure to generate a successful live-fire detection was caused by endpoint prevention rather than a demonstrated detection-logic gap.

The rule was therefore retained without artificially weakening the endpoint security controls.

This was an intentional detection-engineering decision.

---

## 17. Why Security Controls Were Not Disabled

Windows Defender was not disabled or weakened simply to make the detection test succeed.

Doing so would have produced an unrealistic validation environment and would have removed an important security control.

Instead, the project documented the limitation transparently:

```text
Detection Logic: Designed
Detection Configuration: Validated
Attack Execution: Prevented
Successful Detection: Not Demonstrated
```

This provides a more accurate representation of the actual test result.

## 19. Lessons Learned

This test reinforced several important SOC and detection-engineering concepts:

- Credential dumping is a high-risk credential-access behavior.
- Endpoint prevention and SIEM detection are complementary controls.
- A blocked attack does not automatically mean a detection rule is broken.
- Detection validation depends on the underlying behavior producing observable telemetry.
- Security controls should not be weakened simply to make a lab test pass.
- Failed or prevented simulations should be documented transparently.
- Critical credential-access activity requires rapid investigation and escalation.
- Detection engineering includes documenting limitations and coverage gaps.

---

## 20. Final Result

Rule 100404 successfully demonstrated that the intended detection logic was configured and mapped to the correct MITRE ATT&CK technique.

However, the LSASS dumping simulation was prevented by Windows Defender during both automated and manual attempts.

As a result, the rule did not receive successful live-fire validation in this project.

The correct conclusion is therefore:

**Detection Rule: Configured**

**Attack Simulation: Prevented**

**Wazuh Live-Fire Validation: Not Successfully Demonstrated**

**Endpoint Prevention: Successfully Demonstrated**

**Detection Status: UNVALIDATED DUE TO ENDPOINT PREVENTION**
