---

## 1. Detection Objective

The objective of Rule 100403 was to detect execution of `whoami.exe` on the Windows endpoint.

The `whoami` utility displays information about the user account associated with the current session.

Although it is a legitimate Windows utility, attackers may use it during reconnaissance to identify the account under which commands are executing.

The detection was therefore designed to identify `whoami.exe` process creation and provide the SOC analyst with endpoint telemetry for investigation.

---

## 2. MITRE ATT&CK Technique

**T1033 — System Owner/User Discovery**

**Tactic:** Discovery

System Owner/User Discovery involves identifying the account or user associated with a system.

This information can help an attacker understand the privileges and identity context available on a compromised endpoint.

---

## 3. Detection Logic

The rule focuses on process-creation telemetry associated with:

```text
whoami.exe
```

The project used Windows Sysmon process-creation telemetry as the primary data source.

The detection identifies execution of the Windows `whoami.exe` utility and maps the observed behavior to:

```text
T1033
```

---

## 4. Detection Rule

The custom Wazuh rule was created in the Wazuh manager's local rules configuration.

The rule was assigned:

```text
Rule ID: 100403
Wazuh Level: 5
```

and mapped to:

```text
MITRE ATT&CK: T1033
Tactic: Discovery
```

The detection logic focuses on the execution of `whoami.exe`.

---

Before testing the detection, the Wazuh configuration was validated using:

```text

```

This confirmed that the Wazuh configuration could be loaded without errors.

The rule was then tested against the Windows endpoint in the isolated laboratory environment.

The simulation generated execution of:

```text
whoami.exe
```

on the Windows endpoint.

The resulting endpoint telemetry was collected by Sysmon and forwarded to Wazuh.

## 7. Detection Result

### Status: Successfully Fired

Rule 100403 successfully detected the simulated user-discovery activity.

The rule fired **five times** during repeated testing.

The testing included both:

1. Direct execution of `whoami.exe`
2. PowerShell-invoked execution of `whoami.exe`

Both execution paths were correctly detected.

---

## 8. Why Multiple Detections Matter

The five detections demonstrated that the rule was able to consistently identify the targeted behavior during repeated testing.

The testing also showed that the detection was not limited to one particular execution context.

Both direct execution and PowerShell-invoked execution generated matching telemetry.

This is useful from a detection-engineering perspective because attackers may execute the same discovery utility through different parent processes or command interpreters.

---

## 9. Alert Investigation

When investigating a Rule 100403 alert, the analyst should review:

- Timestamp
- Endpoint
- User
- Process image
- Process ID
- Parent process
- Parent command line
- Command line
- Related discovery activity
- Other alerts from the same endpoint

The parent process is particularly useful when determining how the command was executed.

For example, `whoami.exe` launched directly may have different context from the same utility launched through PowerShell as part of a larger command sequence.

## 12. False Positive Considerations

`whoami.exe` is a legitimate Windows utility and may be used during normal administration and troubleshooting.

Potential legitimate uses include:

- System administration
- Troubleshooting
- IT support
- PowerShell scripts
- Security testing
- User-account verification

Therefore, execution of `whoami.exe` should not automatically be considered malicious.

The analyst should determine why the command was executed and whether it forms part of a larger suspicious sequence.

---

## 13. Analyst Investigation Questions

When the alert is triggered, the SOC analyst should ask:

### Who executed the command?

Identify the account associated with the process.

### What launched `whoami.exe`?

Review the parent process and parent command line.

### What happened before the alert?

Search for preceding authentication, execution, or discovery events.

### What happened after the alert?

Look for additional discovery, privilege escalation, persistence, or execution activity.

### Was the activity expected?

Determine whether the endpoint was undergoing administration, troubleshooting, testing, or another authorized activity.

## 17. Detection Engineering Takeaway

This detection demonstrated how a legitimate Windows utility can provide useful security telemetry when monitored as part of an endpoint detection strategy.

The important distinction is that:

```text
Tool execution ≠ Automatically malicious
```

Instead, the SOC analyst must consider:

```text
Process
+
User
+
Parent Process
+
Command Line
+
Timing
+
Related Activity
=
Detection Context
```

This contextual approach helps reduce false positives while maintaining visibility into reconnaissance activity.

---

## 18. Lessons Learned

This detection reinforced several important SOC and detection-engineering concepts:

- User discovery is a common reconnaissance activity.
- Legitimate operating-system utilities can be useful detection points.
- Process-creation telemetry provides valuable endpoint visibility.
- Parent-process information improves alert investigation.
- Repeated testing helps demonstrate detection consistency.
- The same behavior can be executed through different process contexts.
- A triggered alert still requires contextual investigation.
- MITRE ATT&CK provides a structured way to describe discovery behavior.
